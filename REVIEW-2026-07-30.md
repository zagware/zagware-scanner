## Verdict and the through-line

The security engineering here is genuinely considered — fingerprint-based diffing that survives
refactors, an explicit no-raw-secrets discipline in the betterleaks parser, real SHA256 pinning of all
four child binaries, cosign signing, SLSA provenance, and a cooling-period promotion design. Those are
not box-ticking; they are the right controls for the stated threat model. **Do not regress them.**

One defect class undermines the rest, and it is the organising insight of this review:

> **Almost every failure path fails silently in the reassuring direction — in the product *and* in its
> own supply chain.** A crashed scanner, a missing binary, an unresolvable repo visibility, and a
> CVE gate that never runs all render as green builds and ✅ banners.

Concretely, the same bug shape appears in five independent places: `QUAL-01` (SCA/Secrets crash → "0
findings"), `QUAL-02` (visibility unknown → public-repo gate silently off), `SUP-01` (weekly audit can
never alert), `SUP-03` (promotion gate fabricates a number), `SUP-04` (release summary asserts an
unmeasured clean scan). Fixing them individually is correct but insufficient — adopt the rule that
**a control that cannot run must fail loudly**, and apply it as one pass.

Second theme: **several written guarantees are not met by the code.** The raw-secret promise
(`SEC-02`, `SEC-03`), telemetry privacy (`SEC-09`), suppression attribution (`SEC-10`), SLSA Build L3
(`DOC-04`), a Trivy scan that does not exist (`DOC-03`), and an `Apache-2.0` label on a licence file
that is not Apache-2.0 (`DOC-01`). For a product sold on supply-chain rigour these cost more trust
than the honest weaker claim ever would. Where the fix is expensive, **correct the claim** rather than
leaving it overstated.

Publish run `30456276121`'s "Self-scan image with Grype" step completed in **3 milliseconds**

Grype scan of a Debian-based image takes tens of seconds (DB fetch + analysis). The step reports

**2. The promotion CVE gate has never executed.** `promote.yml` has exactly one run in its history

consulted, so the enforced hash is trusted because a human typed it. Scope the fix accordingly —
do not "add pinning", it is already there. → `SUP-07`

## Do not re-audit — surfaces explicitly checked and found clean

effort. Two of them are **load-bearing invariants you must not break** while fixing other findings.

- **YAML injection via the suppression `reason`** — cleared. The command regex is line-scoped, the read
  path splits symmetrically on lines, quotes are escaped, and the `id` written to the file always comes
  from `resolve_suppression_id` and is never attacker-controlled. (Note `QUAL-24` still applies to
  quote/backslash *round-tripping* — that is a correctness bug, not an injection.)
- **`shell=True`** — zero occurrences. All six subprocess sites use list argv. CI enforces this
  (`ci.yml:26-29`); keep it that way.
- **Commit-message injection** — cleared; the interpolated value is an integer.
- **TLS verification** — never disabled anywhere.
- **`ZAGWARE_MIN_SEVERITY` argument injection** — cleared; allowlist-validated before use.
- **Tokens in the PR comment or in artifacts** — cleared. No render path carries one, and git 2.46 strips
  userinfo from clone-failure stderr, so the `exc.stderr` logs are clean. (`SEC-07` is about `.git/config`
  and argv, which is a different sink.)
- **Telemetry thread hangs** — cleared. Daemon threads, 3s socket timeout, bounded 2s flush, all
  exceptions swallowed. Cannot hang a CI job.
- **JSON nesting/depth attacks** — not reachable from repo content; the parsed shape is fixed by the
  three scanners. (Volume-driven memory amplification is real and separate — `SEC-11`.)

**⚠️ Invariants to preserve:**

1. **The secrets-report field discipline is correct and deliberate.** `run_secrets_scan` builds each
   finding from exactly six fields and carries an explicit guard comment at `scanner.py:1224`:
   `# NEVER read f["Secret"], f["Match"], f["MatchContext"], f["CaptureGroups"], f["Line"] here.`
   This is the one place the raw-secret promise is actually kept. **Do not "simplify" it.** Verified
   accurate against `README.md:373-375` (see `DOC-24`).
2. **The IaC failure path is the correct model** for `QUAL-01`. `run_scan` raises `RuntimeError` stating
   "This is NOT 'no findings'; it is a scanner failure." Mirror that shape for SCA/Secrets rather than
   inventing a new convention.

### SEC-01 — [CRITICAL] Enforce author authorization on /zagware suppress before applying or pushing

*Reviewer confidence: 0.95*

**Where:** `src/scanner.py:2320-2325` (dispatch), `1245-1276` (parse), `1333-1359` (write+push), `454-478` (`read_pr_comments`)

**What:** `read_pr_comments()` returns every comment on the PR with no author filter, and the consuming dispatch does not check who wrote it:
```python
comments = platform.read_pr_comments()
commands = parse_suppression_commands(comments)
```
`parse_suppression_commands` records `author` purely for the audit trail (`author = c.get("author") or "unknown"`, line 1258) and never gates on it. Grepping the whole repo, the only `author_association` check lives in workflow YAML — `README.md:68` and `examples/github-actions.yml:64`:
```yaml
contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.comment.author_association)
```
That condition only decides whether an `issue_comment` event *starts a job*. It does not filter which comments the scanner obeys. The workflow also fires on `pull_request: [opened, synchronize, reopened]` with `permissions: contents: write` declared at workflow scope (`examples/github-actions.yml:51-53`), so every ordinary push to the PR starts a run that re-reads all comments, honours a suppress command from **any** author, and has push rights. A user who omits the `if:` block entirely loses even the trigger-level gate.

**Impact:** On a public repo any GitHub user can comment `/zagware suppress <6-hex-prefix> reason`, and on the next push the scanner will (a) drop that finding from the "new findings" diff, (b) neutralise the `ZAGWARE_FAIL_ON_NEW` / `ZAGWARE_SECRETS_FAIL_ON_PUBLIC` merge gate for it (`2461-2470`), and (c) commit and push `.zagware/suppressions.yaml` to the branch under review as `Zagware Scanner <zagware-scanner@users.noreply.github.com>`. The scanner's core promise — that findings a PR introduces are surfaced and can block the merge — is defeated by an unprivileged outsider.

**Fix:** Capture `"author_association": c.get("author_association", "")` in `GitHub.read_pr_comments()` (line 470-474), thread it through `parse_suppression_commands`'s tuple, and in the `main()` loop skip any command whose association is not in an allowlist (default `{"OWNER","MEMBER","COLLABORATOR"}`, overridable via a new `ZAGWARE_SUPPRESS_ALLOWED_ASSOCIATIONS`). Default-deny when the field is absent, and log the rejected author so it is visible in the run.

### SEC-02 — [HIGH] Fix _redact_value: the category test never matches KICS's secret category

*Reviewer confidence: 0.9*

**Where:** `src/scanner.py:1380-1393`, consumers at `1614` and `2104-2107`

**What:** The blanket category-based redaction is keyed on a string KICS never emits:
```python
_SECRET_CATEGORIES = {"secrets", "password", "credential", "key", "token", "authentication"}
...
if any(k in cat_lower for k in _SECRET_CATEGORIES):
    return "***REDACTED***"
```
KICS's category for credential queries is `"Secret Management"`. Verified in Python: `any(k in "secret management" for k in _SECRET_CATEGORIES)` → `False` (`"secrets"` plural does not occur in `"secret management"`; none of the other five do either). Every KICS category — `Secret Management`, `Encryption`, `Insecure Configurations`, `Access Control`, `Best Practices` — tests `False`, so the category branch is dead code and only the five regexes at `1372-1378` ever run. Those require either a `password|token|secret|api_key ... [:=] value` shape or a specific vendor prefix (`AKIA`, `ghp_`, PEM header, JWT). Verified unmatched by all five: `hunter2`, `supersecret123`, `postgres://u:p@db/x`, `xoxb-123456789012-abcdefghijkl` — and `actual_value` from KICS is typically the bare value, not a `key: value` pair.

**Impact:** The one function the whole product relies on to keep secrets out of egress fails open. A hardcoded password, DB connection string, or non-AWS/non-GitHub API key that KICS flags is rendered verbatim into the PR comment table (`1614`) — public and immutable in the PR's comment history — and written verbatim into `zagware-scan-results/iac-*.json`, which `examples/github-actions.yml:92-97` uploads as a 30-day-retained build artifact.

**Fix:** Match KICS categories exactly rather than by substring guess (`_SECRET_CATEGORIES = {"secret management", "encryption"}` compared with `cat_lower in _SECRET_CATEGORIES`), or better, redact `actual_value` unconditionally (allowlist the safe columns instead of blocklisting dangerous strings) and keep the regex pass as a second layer over `expected_value`, which is currently not redacted at all (`1613`).

### SEC-03 — [HIGH] Redact KICS actual_value before uploading results to the platform

*Reviewer confidence: 0.95*

**Where:** `src/scanner.py:1970` and `1986` (payload), `2250` (call site), contrast `2104-2107`

**What:** `upload_to_platform` ships the KICS result dict straight through:
```python
'scanner_version': __version__,
'results': base_results,
```
(and `'results': head_results` at 1986), fed from `main()` at 2250 with the raw parsed KICS output:
```python
upload_to_platform(..., base_results, pr_results)
```
The artifact writer on the very same data deliberately does the opposite (`2103-2107`): `json.dumps(_redact_kics_results(base_results), ...)` with the comment *"redacted KICS JSON — actual_value masked to prevent secret leakage"*. So redaction is applied to the local artifact and skipped on the network egress.

**Impact:** Every KICS finding's `actual_value` — which for the hardcoded-credential queries is the literal secret pulled out of the customer's IaC — is transmitted to and stored by the Zagware SaaS in full, for both base and head scans, on every PR. This directly contradicts `README.md:372` ("Findings never include the raw secret value in the PR comment, platform upload, or scan artifacts") and the module's own stated intent, and it silently widens the blast radius of a platform-side breach to include customer credentials.

**Fix:** Change lines 1970 and 1986 to `'results': _redact_kics_results(base_results)` / `_redact_kics_results(head_results)`, or redact once in `main()` before line 2250 and pass the redacted dicts to both the upload and the artifact writer.

### SEC-04 — [HIGH] Refuse to follow a symlinked .zagware/suppressions.yaml

*Reviewer confidence: 0.9*

**Where:** `src/scanner.py:1421-1425` (read), `1336-1350` (read-modify-write), `1486-1487` (blame stat)

**What:** The suppressions path is joined onto the freshly cloned, attacker-controlled worktree and then opened with plain pathlib calls that follow symlinks:
```python
supp_file = Path(scan_dir) / _SUPPRESSIONS_PATH
if not supp_file.exists():
    return {}
text = supp_file.read_text(encoding="utf-8")
```
and on the write side (1336-1350):
```python
if supp_path.exists():
    current_text = supp_path.read_text(encoding="utf-8")
...
supp_path.write_text(current_text.rstrip() + "\n\n" + "\n".join(yaml_lines), encoding="utf-8")
```
Git stores and checks out symlinks, so a PR can commit `.zagware/suppressions.yaml` as a symlink to any path. There is no `is_symlink()`, `resolve()`-containment, `O_NOFOLLOW`, or size check anywhere on this path. `load_suppressions()` runs on **every** scan (`2213`), needing no comment and no privilege.

**Impact:** Three distinct outcomes, all from a hostile PR against a repo that runs this scanner: (1) *arbitrary read* — the link target is read and every `id:`/`reason:`-shaped line becomes a suppression record whose `reason` is uploaded to the SaaS at `1888`/`1918`, exfiltrating file content off the runner; (2) *arbitrary write as root* — once any suppress command resolves, `write_text` truncates and rewrites the link target inside the scanner container, with an attacker-chosen `reason` string appended; (3) *DoS* — a symlink to `/dev/zero` or `/dev/urandom` makes `read_text()` consume all memory before the bare `except Exception` at `1426` can help.

**Fix:** In both `_parse_suppressions_file` and `apply_suppression_commands`, reject the path when `supp_file.is_symlink()` is true or when `supp_file.resolve()` is not relative to `Path(scan_dir).resolve()`; open with `os.open(..., os.O_RDONLY | os.O_NOFOLLOW)` and cap the read at a fixed size (e.g. 1 MiB) before decoding.

### SEC-05 — [MEDIUM] Drop Authorization on cross-host redirects, add a timeout to _http, require https for the platform URL

*Reviewer confidence: 0.85*

**Where:** `src/scanner.py:278-292` (`_http`), `1922`/`1958`/`2017`/`2055` (uploads), `2244-2245` (URL intake)

**What:** Three defects on one axis. (1) `urllib.request.urlopen` follows 30x redirects by default and preserves `Authorization`. Verified against CPython's `HTTPRedirectHandler.redirect_request`, which strips only content headers: redirecting a `POST https://a.example/x` carrying `Authorization: Bearer SEKRET` to `https://evil.example/y` yields a new request whose headers are exactly `{'Authorization': 'Bearer SEKRET'}`. This applies to every upload (`1922`, `1958`, `2017`, `2055`) and every `_http` call. (2) `_http` alone has no timeout — `with urllib.request.urlopen(req) as resp:` (line 285) uses the global default of `None`; the uploads use `timeout=30` and telemetry uses `3`. (3) `ZAGWARE_PLATFORM_URL` is consumed with no scheme or host validation:
```python
_platform_url = os.environ.get('ZAGWARE_PLATFORM_URL', '').rstrip('/')
```
and interpolated directly (`f'{platform_url}/api/v1/iac/upload'`), so `http://` is accepted.

**Impact:** If a self-hosted platform endpoint is compromised, misconfigured, or reached over `http://` (accepted today), it can 302 the upload to any host and the `gtp_…` `ZAGWARE_PLATFORM_TOKEN` — plus the full scan results — follow to the attacker. The same redirect behaviour would relocate `GITHUB_TOKEN`/`GITLAB_TOKEN`/`SYSTEM_ACCESSTOKEN` on the `_http` paths, where `CI_SERVER_URL` and `SYSTEM_TEAMFOUNDATIONCOLLECTIONURI` are already operator-supplied hosts. The missing timeout means one stalled socket to `api.github.com` inside the comment-pagination loop (`430-440`) hangs the pipeline until the CI platform's global job timeout.

**Fix:** Build one `urllib.request.OpenerDirector` with an `HTTPRedirectHandler` subclass whose `redirect_request` returns `None` when `urlsplit(newurl).netloc != urlsplit(req.full_url).netloc`, and route every request through it; add `timeout=30` at line 285; validate at `2244` that `urlsplit(_platform_url).scheme == "https"` (allowing `http` only for localhost) and refuse the upload with an explicit log line otherwise.

### SEC-06 — [MEDIUM] Escape attacker-controlled file names, resource names, and package names in the PR comment

*Reviewer confidence: 0.85*

**Where:** `src/scanner.py:1611`, `1682`, `1746`, `1809`; sanitiser at `1367-1369`

**What:** `_cell()` is the only escaper and it is weak and narrowly applied:
```python

    text = text.replace("|", "\\|").replace("\n", " ").strip()
```
It handles only `|` and `\n` — not a backtick, `<`, `>`, or `\r` — and only two of six IaC columns pass through it (`1613-1614`). Everything else is interpolated raw from values a PR fully controls:

L.append(f"| `{rule_cell}` | `{f.get('file_path','')}` | ...")  # 1746  secrets file path

**Impact:** A PR can add a file or a lockfile package whose name contains a backtick plus markup and make the scanner's own bot comment render forged content — `</details>` to escape the collapsed section, an `<img src=…>` beacon (GitHub's comment sanitiser permits `img`, `a`, `details`, `b`), or a fabricated `✅ **No new security findings introduced by this PR.**` line. **Fix:** Extend `_cell` to also escape backticks (or wrap values in a length-aware code fence), `<`, `>`, and `\r`, and route every interpolated finding-derived value at `1611`, `1682`, `1746`, and `1809` — file names, resource names, issue types, package names — through it rather than only `expected_value`/`actual_value`.

### SEC-07 — [MEDIUM] Keep the CI token out of git argv and .git/config

### SEC-09 — [MEDIUM] Send $geoip_disable and stop claiming the repo hash is irreversible

*Reviewer confidence: 0.9*

**Where:** `src/scanner.py:185`, claim at `116`, `_telemetry_identity` at `152-172`, docs at `README.md:694-704`

**What:** Two stated privacy guarantees do not hold. (1) `props["$ip"] = 0  # disable PostHog IP-based geolocation`. PostHog's GeoIP plugin does `let ip = event.properties?.$ip || event.ip` and then `if (ip && !event.properties?.$geoip_disable)` (PostHog/posthog-plugin-geoip `index.ts`). `0` is falsy in JS, so it is discarded and the plugin falls back to `event.ip` — the runner's public IP — and geolocates normally. The documented switch is `$geoip_disable: true`. (2) `repo_hash = _telemetry_hash(f"{platform_name}:{repo_full_name}")` is an unsalted SHA-256 truncated to 16 hex chars over a small, public, fully enumerable namespace (GitHub `owner/repo` strings); a precomputed table over public repo lists reverses it directly, and `org_hash = _telemetry_hash(org)` even more easily.

**Impact:** `README.md:701-702` tells users the identity is "**not** reversible to your actual repo/org name by Zagware or anyone with PostHog access", and `README.md:694-696` lists "IP-based geolocation (`$ip: 0` is set explicitly to disable PostHog's IP capture)" under "What is never sent". Both are false as written: for any public repo, Zagware or anyone with access to the PostHog project can recover the exact `owner/repo`, and the runner's IP is captured and geolocated on the default (telemetry-on) path. That is a misrepresentation in a security product's privacy statement, and the IP is a third-party-processor disclosure users were told did not occur.

**Fix:** At line 185 set `props["$geoip_disable"] = True` and `props["$ip"] = None`. For identity, either drop `repo_id`/`org_id` entirely or HMAC the name with a per-install random value persisted outside the repo; either way correct `README.md:699-704` to describe the value as pseudonymous-but-linkable rather than irreversible.

### SEC-11 — [LOW] Avoid multiplying peak memory over scanner output on a hostile repo

*Reviewer confidence: 0.7*

**Where:** `src/scanner.py:1026-1027`, `1400-1403`, `2104-2107`

**What:** Grype's entire JSON report is captured into memory as a Python `str` and then re-encoded on write:
```python

    Path(grype_out).write_text(r.stdout)
```
(`capture_output=True` at `1020`), then read back and parsed at `1059`. On the KICS side, redaction deep-copies the whole result set and serialisation pretty-prints it twice:

### SEC-16 — [LOW] Terminate git option parsing before passing refs from the environment

*Reviewer confidence: 0.7*

**Where:** `src/scanner.py:899-900`, `1358`

**What:** Refs derived from the environment are passed in a position where git still parses options:
```python
_git(["fetch", "--depth=1", "origin", sha], cwd=dest)   # 899
_git(["checkout", sha], cwd=dest)                        # 900
_git(["push", "origin", head_branch], cwd=pr_dir)        # 1358
```
Verified that git 2.46 does parse a leading-dash value in that slot as an option rather than a refspec: `git fetch --depth=1 origin --upload-pack=/bin/false` → `/bin/false 'origin': /bin/false: No such file or directory`. The value flowing in is `head_branch`, i.e. `ZAGWARE_HEAD_REF` / `GITHUB_HEAD_REF` / `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME` / `BITBUCKET_BRANCH` (`403-405`, `551-552`, `645`) — the PR source branch name, chosen by the contributor. `--branch <x>` at `889`/`895` is *not* affected: git's parse-options consumes the next argv as the option value unconditionally.

**Fix:** Use `["fetch", "--depth=1", "origin", "--", sha]`, `["checkout", "--detach", sha]`, and `["push", "origin", "--", head_branch]`, and validate refs once at intake in `main()` (`2179-2181`) against `^[A-Za-z0-9][A-Za-z0-9._/-]*$` or `^[0-9a-f]{7,40}$`, failing the run with a clear message otherwise.

But the reporting is exclusive: `exit_code = 1 if (_FAIL_ON_NEW and new_total > 0) else 0` (2466); `if _SECRETS_FAIL_ON_PUBLIC and repo_visibility == "public" and novel_secrets: exit_code = 1; log.warning("Exiting 1 — %d new secret(s) in a PUBLIC repository ...")` (2470-2473); `elif exit_code: log.warning("Exiting 1 — %d new finding(s) (ZAGWARE_FAIL_ON_NEW=true)", new_total)` (2474-2475). When a public repo has both a new secret and new IaC/SCA findings, only the secrets message is logged. telemetry_flush() in __main__ (2490) cannot alter the exit code — it only joins daemon threads with a bounded deadline and cannot raise — so the exit path is sound; the cost is up to 2s of wall time on every run, including runs that exit 0.

**Impact:** An operator reading the tail of a failed build log sees only the secrets reason, may fix the credential expecting green, then hit a second failure for IaC findings that were never mentioned.

**Fix:** Make the second branch independent — `if exit_code and _FAIL_ON_NEW and new_total > 0:` — so both reasons are logged, and consider collecting reasons into a list rendered as a single `Exiting 1 — <reason>; <reason>` line.

### SUP-01 — [HIGH] Make audit.yml's CVE gate fail closed so the weekly alert can fire

*Reviewer confidence: 0.95*

Where: .github/workflows/audit.yml:50-58. `SCAN_OUTPUT=$(grype ... 2>&1) || true` then `HIGH_COUNT=$(echo "$SCAN_OUTPUT" | jq '...' 2>/dev/null || echo "0")`. Grype is not installed, so SCAN_OUTPUT is 'grype: command not found', jq exits non-zero on non-JSON, and `|| echo "0"` fabricates a clean result. The alert step's gate `steps.scan.outputs.high_count != '0'` (line 60) can therefore never be true. Impact: the only continuous control over the :stable image customers pin reports a green 'No new HIGH/CRITICAL vulnerabilities found' (line 96) every Monday forever, whether or not the image is vulnerable. Fail-open and undiscoverable. Fix: install Grype (anchore/scan-action pinned to a SHA, or a SHA-pinned installer), remove `|| true` so a missing binary fails the step, and replace the default with `jq -e ... || exit 1` so a parse failure is an error rather than 0. Add a `command -v grype` assertion at job start.

### SUP-02 — [HIGH] Reject reserved tags on workflow_dispatch and make :latest conditional
